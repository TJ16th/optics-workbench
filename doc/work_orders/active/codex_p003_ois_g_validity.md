# P003：OIS_G群定義の物理的妥当性確認 指示書（Codex向け）

## 背景

P3-0報告によると、P003（アクロマートダブレット）に追加した`OIS_G`（手ブレ補正群）は`S2`〜`S3`の範囲として定義されている。P003はアクロマートダブレット（2枚接合レンズ）であり、もしS2・S3が接合面を挟む2枚のガラスの片方ずつを指しているなら、**手ブレ補正群が接合レンズの片割れだけを動かす**という物理的にありえない設定になっている（接合レンズは1つの塊として製造・動作するため、分離してシフト/チルトすることはできない）。

## 作業

1. P003の面構成を確認する：S1・S2・S3がそれぞれ何を表しているか（材質境界、接合面かどうか）を`presets.ts`の定義から確認する。
2. `OIS_G`の範囲（S2〜S3）が、実際に接合面をまたいでいるか確認する。
3. 接合面をまたいでいる場合、これは設計ミスである。以下のいずれかに修正する：
   - (a) `OIS_G`の対象を、接合ブロック全体（例：S1〜S3、レンズ全体）に変更する。
   - (b) 手ブレ補正群としてより適切な独立要素（例：別途薄レンズ群を追加する等）に差し替える。
   - どちらが適切か、P003の教育目的（アクロマート色収差確認）を損なわない範囲で判断し、報告する。
4. 修正後、近軸検証（9.1節の数値検証規約）を再実行し、破綻しないことを確認する。
5. 同様の問題が`FOCUS_G`や他のプリセットの群定義にも無いか、横断確認する。

## 完了条件

- OIS_G（および他の群）が、物理的に独立して動かせる要素のみを対象にしていることが確認・修正されている。
- 修正後の近軸検証結果が報告されている。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを確認する。

本タスクとは別件だが、`doc/reports/issues_backlog.md`に以下2件を追記する（AGENTS.mdのGitHub Issue運用節のフォーマットに従う。内容の実装はここでは行わない、登録のみ）：

1. タイトル：`edge_thickness metricのエンジン実装を追加する`
   - ラベル案：`engine`
   - 背景：仕様・`/v1/meta`のmetadata列挙には`edge_thickness`が存在するが、エンジン本体に算出コードが見当たらないことがLayout View品質改善タスクで判明した。
   - 対応案：仕様10.3節の定義（`min(semiD_a, semiD_b)`位置での周縁厚評価）に従い、実際の算出ロジックを実装する。
   - 受け入れ条件：`edge_thickness`オペランドがevaluate APIで実際の数値を返す。既存のedge thickness警告経路と整合する。

2. タイトル：`最適化APIにmulti-configuration（複数zoom_position/フォーカス位置）評価を追加する`
   - ラベル案：`engine`, `architecture`
   - 背景：ズーム・フォーカス・防振群の実務的な設計最適化は、複数のconfiguration（広角端・望遠端、無限遠・至近等）を同時に評価し全域でバランスした解を探す必要がある。現行のオペランドAPI（25.3節）・ヤコビアンバッチ（25.7節）は単一configurationのみ対応で、`zoom_positions`（10.2節）とは接続されていない。
   - 対応案：各オペランドにconfiguration_id/zoom_position_idを持たせ、複数configurationを1回のevaluateでまとめて評価しmerit合成する仕組みを検討する。詳細設計は別途エンジン仕様改訂で行う（本Issueは登録のみ、着手は最適化タスク8-13の前提整理時）。
   - 受け入れ条件：（設計検討タスクのため）まずエンジン仕様への追記案が作成されること。
