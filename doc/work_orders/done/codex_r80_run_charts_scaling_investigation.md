# R80：Run Chartsの実行時間が構成枚数・多構成(zoom/focus)評価数に依存するかの調査 指示書（Codex向け）

## 背景

R76（field密度3→16）・R78（MTF周波数5→33点）・R79（MTF専用ray数9→4096本）と、精度向上を目的にサンプル数を段階的に増やしてきた結果、人間からRun Chartsの表示に体感で時間がかかるようになったとの指摘があった。これ自体はサンプル数増加の副作用として想定内だが、人間から次の2点が未確認のまま気になるとの指摘があった。

1. Run Chartsの実行時間は、レンズの構成枚数（面数）に依存するか。
2. ズーム・フォーカス位置を複数評価する場合、単純に評価するposition数に比例して時間が増えるのか。

②については、本台帳のR5詳細（`## 次にやること`直前セクション「R5詳細：multi-configuration最適化の設計負債」）で、**最適化オペランドAPI（25.3節・25.7節）は1回のevaluate呼び出しにつき単一configurationしか扱えず、複数configurationにまたがる評価の仕組みが存在しない**ことが既に判明している。この制約が通常のAnalysis/Run Chartsエンドポイント（最適化とは別系統）にも同様に当てはまるか、実データで確認すること。

比較用プリセットは、面数の異なるP002（2面、単玉）・P007（4面、正負2枚組）・P012（8面+STOP、テッサー型4枚3群）を使う。**P011（10面、対称6枚Planar/Xenon型ダブルガウス）は比較対象から除外する**。理由：R67完了報告で、P011は25-ray throughputでalive213/aiming_failed12（周辺fieldでのfull aiming収束失敗、開口遮光によるものではない）と記録されており、人間からも「周辺の光線がちゃんと像面に届いていない」との指摘があった。この既知の未解決挙動が時間計測・alive光線数に交絡するため、本タスクでは公平な比較にP012を用いる。P011自体の光線到達問題は本タスクの対象外とし、作業の最後にissues_backlog.mdへ独立した項目として登録すること（詳細は作業3参照）。

## 作業

### 1. 構成枚数と実行時間の関係の実測

1. P002（2面）・P007（4面）・P012（8面+STOP）で、同一のfield数・wavelength数・ray samplingパラメータ（既定値のRun Charts、または明示的に固定した条件）を用い、実UIまたは実API経由でRun Charts全体（7種の解析）の実行時間を複数回測定する。
2. 面数と実行時間の関係が線形か、それ以上（超線形）か、ほぼ無関係かを、実測値の表で示す。単純な回帰計算ができるならその結果も付記する。
3. 個々の解析（Ray Fan / Spot / MTF / 像面湾曲 / 周辺光量 / 歪曲 / 縦収差図等）のうち、面数依存が大きいものと小さいものがあれば、その内訳も示す。

### 2. 複数configuration（zoom/focus position）評価のコストモデル確認

1. 現行のAnalysis系API・UIに、複数のzoom_position/group位置を1回のリクエストでまとめて評価する仕組みが存在するかどうかをコード・APIレスポンスで確認する。存在しない場合、UIでズーム・フォーカス位置を切り替えてRun Chartsを再実行する際、system再登録（re-registration）から解析完了までに必要な処理が何かを明らかにする。
2. P003（既存の群操作対応プリセット）等、zoom_position/groupの切り替えが可能なプリセットを使い、position数を1、3、5点等と変化させながら「position数×Run Chartsを実行した場合」の合計時間を実測する。
3. 合計時間が単純にposition数に比例するか、切り替え自体に追加の固定コスト（system再登録・キャッシュ無効化等）がかかりそれ以上に増えるかを実測値で示す。
4. 複数configurationを1回のAPIコールでまとめて評価する仕組みが存在しないことが確認された場合、これがR5詳細に記録された最適化API側の制約と同じ設計上の欠落（multi-configuration operand未対応）に起因するのか、それとも別の理由によるものかを明らかにする。

### 3. P011の周辺光線未到達問題のbacklog登録

1. R67完了報告のaiming_failed12件について、現行コードでも同じ挙動が再現するかを軽く確認する（深追いした原因調査は本タスクの対象外）。
2. `issues_backlog.md`へ、「P011: 周辺fieldでfull aiming収束が失敗し、周辺光線が像面に到達しない」という項目を、既知の実測値（alive213/aiming_failed12等）付きで新規登録する。本タスクでは実装修正は行わない。

## 完了条件

- P002/P007/P012でのRun Charts実行時間が、複数回実測値の表で示され、面数との関係（線形/超線形/無関係）が結論付けられている。
- 複数configuration評価について、現行APIに一括評価の仕組みがあるかどうかが実データで確認され、無い場合はposition数と合計時間の関係が実測されている。
- 上記2点の結論が、人間の「面数依存」「position数に単純比例」という仮説それぞれについて、実測に基づき肯定・否定・部分的に正しい、のいずれかで明確に述べられている。
- P011の周辺光線未到達問題がissues_backlog.mdへ新規登録されている（本タスクでは修正しない）。
- 本タスクは調査のみであり、既存の挙動・性能への変更は行わない（コード修正は行わない）。
- 完了報告に、実測値の取得方法（API直接呼び出しか実UI操作か）を明記する。

## 注意

- 「面数に依存する／しない」「position数に比例する／しない」という結論は、目視や理論だけでなく必ず複数回の実測値で裏付けること。
- 本タスクは調査のみであり、性能改善の実装（キャッシュ導入、バッチAPI追加等）は対象外。改善が必要と判明した場合は、その設計方針・規模感（小/中/大）を報告書に記載するに留める。
- P011自体の周辺光線未到達問題の原因調査・修正は本タスクの対象外（作業3のbacklog登録のみ行う）。
