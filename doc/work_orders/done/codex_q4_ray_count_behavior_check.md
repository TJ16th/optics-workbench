# 光線数変更時の表示挙動検証 指示書（Codex向け）

## 着手タイミング

**Layout View描画品質改善（`codex_q1_layout_view_rendering_quality.md`）の完了報告後に着手する。** 現在進行中のタスクと競合しないよう、それまでは着手しない。

## 背景

P002で光線数（Preview/Analysis設定の本数コントロール）を変えると、光線の「表示具合」自体が変わって見えるという違和感が人間から報告された。具体的には、9本設定の時点で軸上・軸外の光線が同時に表示されているが、本数を変えるとこのパターンが変化するように見える。

本来、光線数（`samples_per_field`）は「1つのfieldあたりの密度」を決めるパラメータであり、評価するfieldの集合（軸上・軸外の構成）、瞳サンプリング方式（`pupil_distribution`）、ray aimingのモード（`ray_aiming.mode`）とは独立であるべき（エンジン仕様15章・20章）。もしUI側の「光線数」コントロールがこれらを意図せず連動させているなら、それが違和感の原因である可能性が高い。

## 作業

1. **現状のマッピングを確認する**：UIの光線数コントロール（スライダーまたは数値入力）が、実際に送信するリクエストのどのフィールドを変更しているか確認する（`ray_sampling.samples_per_field`のみか、`fields`配列や`ray_sampling.pupil_distribution`、`ray_sampling.ray_aiming.mode`も一緒に変えていないか）。
2. **決定的な比較を行う**：P002に対し、光線数を最低4パターン（例：5, 9, 15, 25）でPreview/Analysisリクエストを送り、それぞれの**実際に送信されたリクエスト全文**（fields、samples_per_field、pupil_distribution、ray_aiming.mode）と、応答されたpaths（本数・fieldごとの内訳）を記録する。
3. 比較結果から、光線数以外の要素（fields構成、distribution方式、aimingモード）が意図せず変化していないか確認する。
   - 変化していなければ：「密度が変わるだけで、見た目のパターン変化は光線本数増加に伴う自然な変化（fanが密になる等）である」ことを結論づけ、人間が誤解しやすい表示（例えば低本数時に偶然対称に見える等）であれば、その理由も説明する。
   - 変化していれば：どのパラメータが意図せず連動しているかを特定し、光線数コントロールが`samples_per_field`のみを変更するよう修正する。fields・distribution・aimingモードはそれぞれ別のUIコントロール（P2-1で実装済みの解析条件編集UI）でのみ変更されるべきである。
4. 修正の有無にかかわらず、この比較結果をデバッグ用途で人間が再検証できる形にする：
   - UIのDebugタブ（build_info表示と同じ場所）に、直近のPreview/Analysisリクエストで実際に送信された`ray_sampling`全体（samples_per_field, pupil_distribution, ray_aiming.mode, fields一覧）を表示するパネルを追加する。
   - これにより、以後は光線数を変えるたびに「実際何が変わったか」をブラウザ上で即座に確認できるようにする。
5. 簡単な回帰テスト（P002で光線数のみを変えたリクエストがfields/distribution/aimingモードを変えないことを確認するテスト）を追加する。

## 完了条件

- 光線数コントロールと実際のリクエストパラメータの対応関係が報告されている。
- 4パターンの比較結果（送信内容・応答内容）が報告されている。
- 意図しない連動があれば修正され、無ければ「連動なし、見た目の変化は密度増加による自然な変化」と結論づけられている。
- Debugタブでray_sampling内容を確認できるようになっている（人間が今後同様の違和感を持った際、自分で検証できるように）。
- 回帰テストが追加されている。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを確認する（AGENTS.mdの規約通り）。
