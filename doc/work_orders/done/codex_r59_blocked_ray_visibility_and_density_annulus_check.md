# R59：ブロック光線の可視化方針／密度光線のannulus整合性 調査 指示書（Codex向け）

## 背景

R58完了後の目視確認で、人間から関連する2つの疑問が挙がった。

### Part 1：STOP以外の面で遮蔽された光線が非表示になっている

R57のデータで、P005のmid-y/edge-yフィールドの`marginal_upper`が「`blocked`、path: `STOP -> M1`」となる例が既に確認されている。これは絞り自体での完全遮蔽（例：軸上chiefがSTOP中心で即blockedになるケース、path 1点のみ）とは異なり、**M1の有効径外に当たって遮蔽された、意味のある部分パスを持つ光線**である。

現在の描画ルール（R28cで確立）は「`alive`または`aiming_failed`かつ2点以上のpathを持つものだけを描画」であり、`blocked`は理由を問わず一律非表示になっている。「絞りで完全に遮られた」ケースと「途中の鏡の縁で蹴られた（vignetting）」ケースを区別せず同じ非表示扱いにしてよいのか、可視化する価値があるのではないか、という論点。

なお、M1・M2のようなミラー自身が有効径で光線を遮ることは、engine_spec.md 17.3節・R53で確認済みの正しい仕様（外径側遮光は全面種別に適用）である。「ミラーの左に絞りを追加すべきか」という論点は不要と人間・AI双方で確認済み。あくまで「仕様通りに起きている遮蔽を、UIでどう見せるか」の話である。

### Part 2：density rayがannulusの開口帯を正しく尊重しているか

R58でannulus STOPの実際の開口帯（inner〜outer）が正確に可視化されるようになったことで、「実際に撮像面（IMG）まで到達する光線は、本当にこの開口帯を通っているのか」を目視で確認しやすくなった。

baseline（chief/marginal）のannulus遮蔽機能はR40/R41で確認済みだが、**density ray（スポット図等に使う多数サンプル光線）が同じannulus制約を正しく受けているかは未確認**。baselineとdensityでサンプリングロジックが異なる場合、density側にannulus制約が正しく反映されていない可能性がある。

## 作業

### 1. ブロック光線の実態調査

1. P005で、mid-y/edge-yのような、STOP以外の面（M1・M2等）で`blocked`となる光線が、fieldごとにどのくらいの頻度・位置で発生しているかを確認する。
2. `blocked`ステータスの光線を、2点以上のpathを持つもの（意味のある部分軌跡がある）と、1点のみ（STOPで即遮蔽等）のものに区別して集計する。
3. 現在の描画ロジックが、この区別なく全ての`blocked`を一律非表示にしていることをコードで確認する。

### 2. density rayのannulus整合性検証

1. P005で、density rayが実際にSTOP位置でどのY座標を通っているかを取得する。
2. `alive`（撮像面IMGまで到達している）とされるdensity rayについて、STOP通過Y座標の絶対値が実際に`inner_semi_diameter_mm`〜`outer_semi_diameter_mm`の範囲内に収まっているかを検証する。
3. 範囲外を通っているのに`alive`として扱われている光線があれば、annulus制約がdensity ray生成ロジックに正しく適用されていないバグと確定し、原因を特定する。全て範囲内であれば、仕様通りであることを数値で報告する。

### 3. 修正（Part 2でバグが見つかった場合のみ）

- density rayの不整合が見つかった場合は原因を修正する。R40/R41のannulus実装漏れと同種の見落としである可能性を念頭に置く。
- 問題がなければ、コード修正は不要（調査結果の報告のみでよい）。
- Part 1（ブロック光線の可視化方針）は、この指示書ではUI変更を行わず、調査結果と対応案の提示までとする。

## 完了条件

- Part 1：`blocked`光線の発生状況（部分パスを持つものの有無・頻度）が実データで報告されている。可視化方針の対応案（現状維持／新しい線種で表示する等、複数案があれば列挙）が提示されている。この場での実装は必須としない。
- Part 2：density rayのSTOP通過Y座標とannulus inner/outerとの整合性が、実データで数値検証・報告されている。
- Part 2で不整合が見つかった場合は修正され、回帰テストが追加されている。修正を行った場合はスクリーンショットが`doc/reports/screenshots/`に保存され報告書から参照される。既存テストがグリーン。
- コード変更を伴う場合、プロセス再起動後の`build_info.git_commit`とHEADの一致を断定形で報告する（未来形で締めない）。
- **実装根拠には、コミットメッセージだけでなく実際のコミットハッシュ値を必ず併記する。**

## 注意

- 目視の印象で結論を出さず、必ず実データ（field別status・座標）で確認すること。
