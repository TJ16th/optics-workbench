# R99：UI/UXレイアウト全面見直し 設計提案依頼（Codex向け）

## この指示書の性質（重要）

**本タスクは実装ではなく、設計案の提案のみを目的とする。** R84（ヤコビアンバッチモード設計提案）と同じ枠組みで進める。

- 本タスクではproduction codeを変更しない。
- 提案は複数の選択肢とトレードオフを示すこと。1案に決め打ちせず、推奨案とその理由、却下した代替案とその理由を両方示す。
- 最終的な採否・仕様確定・実装指示書の発注は人間とClaude側が行う。人間・Claude側でも独立に別案のモックアップを検討しており、Codexの提案がそのまま採用されるとは限らないことを前提に、判断材料としての質を優先すること。

## 背景

人間から、Workbench UI全体のレイアウトについて次の指摘・要望があった。

- プリセット選択のプルダウンメニューが見づらい。
- 画面レイアウトを全般的に見直すべきではないか。

要望の具体的なイメージは次の4点。

1. 1920×1080を想定し、スクロールは極力避ける。
2. UIの操作と、その結果が同一画面内で確認できる（操作結果がすぐに確認できる）。
3. UXシナリオの流れに合っている。
4. ダークモード・ライトモードの両方をサポートする。

加えて、人間からナビゲーションについて「上部タブより左サイドバー、開閉可能なアコーディオン形式が好み」との追加意見が出ている。この意見は絶対条件（決め打ち）ではないが、**必ず検討対象の1案として真剣に評価すること**。具体的には、下記2.のレイアウト再設計案において、「左サイドバー＋開閉可能なアコーディオンナビゲーション」案を最低1つの具体的な代替案（上部タブ案等）と並べて比較し、それぞれの長所・短所（1920×1080での占有面積、開閉時の情報密度変化、階層が深くなった場合の拡張性、操作と結果の同一画面表示への影響等）を明示すること。その上でCodexとして推奨する構成を結論づけてよい（人間の好みをそのまま採用する必要はないが、「検討せず却下」「検討せず採用」のどちらも不可とする）。

現行UIは`apps/workbench-ui`にあり、System/Preview/Analysis/Compare/Debugタブ構成（上部タブと推定されるが、実装を必ず確認すること）。R92で追加されたThrough-focus MTFチャートのように、専用画面へ分離された機能もある。

## 依頼内容（提案してほしいこと）

以下の論点について、コードベース（`apps/workbench-ui/src`の実装、既存のタブ構成・状態管理・レスポンシブ対応の有無等）を実際に確認した上で、具体的な設計案を提案すること。

### 1. 現状分析

- 現行のタブ構成・画面遷移・状態保持の仕組みを整理する。
- 1920×1080でスクロールが発生している箇所を具体的に洗い出す（どのタブ・どの要素で、どの程度のスクロール量が発生するか）。
- 「操作と結果が同一画面にない」ことで往復操作が必要になっている箇所を具体的に洗い出す（例：条件設定タブと結果表示タブが分かれている、等）。
- プリセット選択UIの現状の問題点（見づらいと指摘された具体的な理由：選択肢数、表示形式、階層構造の有無等）を分析する。
- ダークモード・ライトモードの現状のサポート状況を確認する（CSS変数化されているか、ハードコード色がどの程度あるか）。

### 2. レイアウト再設計案

- ナビゲーション構造（タブ位置、階層、開閉可否を含む）の提案。背景に記載した「左サイドバー＋アコーディオン」案を含む複数案の比較検討をここに記載する。
- 「操作と結果を同一画面内に収める」ための画面分割案（例：条件パネル＋結果パネルの並置、等）。
- プリセット選択UIの改善案（検索・グルーピング・カテゴリ分け等）。
- 1920×1080でスクロールを避けるための情報密度・省略/展開の方針。
- 既存のUXシナリオ（プリセット選択→条件設定→Layout確認→Analysis確認、のような一連の流れ）に対して、提案レイアウトがどう追従するかの説明。

### 3. ダークモード・ライトモード対応

- 実装方式の提案（CSS変数化の範囲、既存のCarbon Design System利用箇所との整合、切替UIの位置）。
- 既存コンポーネント（チャート、Layout View等）で色のハードコードがある場合、対応が必要な箇所の洗い出し。

### 4. 規模感・段階的導入案

- 実装規模を小/中/大で見積もり、根拠を示す。
- 一度に全て変更するのではなく、段階的に導入する場合のロードマップ案（影響範囲の小さいものから、等）。
- 既存の回帰テスト（Playwright E2E等）への影響見積もり。

## 成果物の形式

`doc/reports/`へ、提案書としてMarkdownで提出すること。実装報告ではなく提案書であることが分かるよう、タイトル・冒頭に明記すること。最低限、次を含める。

- 現状分析（1.の内容、実測・実装確認に基づく）
- 推奨案（2.・3.の具体的な設計）。可能であればワイヤーフレーム相当の説明（ASCIIレイアウト図やコンポーネント構成の文章表現等）を含める。
- 検討した代替案とその却下理由
- 規模感（小/中/大）と段階的導入ロードマップ
- 未解決の疑問点・Claude/人間の判断が必要な論点があれば明記する

## 注意

- 繰り返しになるが、本タスクは実装ではなく提案である。「実装しました」ではなく「このように実装することを提案します」というトーンで書くこと。
- 目視の印象ではなく、実装コード・実測（DOM高さ、スクロール発生有無等）に基づいて現状分析を行うこと。
- 既存のCarbon Design System採用方針、既存のi18n（日英）対応方針とは矛盾しない提案とすること。
