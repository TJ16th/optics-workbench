# R74：像面湾曲・周辺光量のサンプリング依存性 現状調査 指示書（Codex向け）

## 背景

人間から、Analysisパネルの像面湾曲（Field Curvature）・周辺光量（Relative Illumination）について、現在のプレビュー解析条件（`ray_sampling`：preview/standard/high_density等の共有プリセット、`doc/ui_spec.md` 13.1〜13.2節）にどこまで依存しているか、依存の仕方が仕様として妥当か、という疑問が出た。

`doc/engine_spec.md`を確認したところ、設計意図としては以下のように、2つの解析でサンプリング依存性の性格が大きく異なる。

- **像面湾曲・M/S像面（21.2節）**：同軸系（現行プリセットは全てこれに該当）では既定でCoddington方程式（主光線1本＋各面の漸化式による解析計算）を使う規定であり、原理的に瞳サンプリング数に依存しない。RMS探索方式（実際に瞳上へ光線を撒く、サンプル数依存）は偏芯・チルト系での既定、同軸系ではあくまで相互検証用のオプション。
- **歪曲（21.3節）**：主光線1本＋固定の基準近軸EFLで計算し、「解析条件によって値が揺れることを防ぐ」ことが明記されている。
- **周辺光量（16.5節・21.4節）**：入射瞳の見込み立体角内で光線を撒き通過率を積算する、Monte Carlo的な積分として定義されている。原理的にサンプル数に依存し、20.2節の推奨サンプル数表でも「1000〜100000 rays/field」と、Ray fan（21〜101本）等より桁違いに多いサンプル数を要求している。

R71で確認された通り、UIの「Run Charts」既定条件は`9 rays / grid / paraxial`である。この少数サンプルが周辺光量にもそのまま使われているとすれば、仕様が要求する精度（1000〜100000 rays）に遠く及ばない可能性がある。一方、像面湾曲は原理的にサンプル数と無関係のはずだが、実装がCoddington方式を実際に使っているかは未確認である。**これらは全て仕様書からの推測であり、実装コードでの確認が必要。**

## 作業1：像面湾曲・M/S像面の実装確認

1. 現行APIが同軸プリセット（P002、P003等）に対して実際にCoddington方式を使っているか、コードとAPIレスポンスのmetadata（`method`フィールド等、21.2節の出力例を参照）で確認する。
2. `ray_sampling`条件（preview/standard/high_density等でサンプル数を変える）を変えても、像面湾曲・M/S像面の出力値が変化しないことを実際にAPIへ複数回異なる条件でリクエストし、数値を突き合わせて確認する。変化する場合は、原因（RMS探索方式が使われている、Coddington方式にも何らかのサンプル依存が紛れ込んでいる等）を特定する。

## 作業2：周辺光量の実装確認

1. 現行APIが周辺光量計算に使用しているサンプル数が、UIの共有`ray_sampling`設定（preview等）から直接渡されているのか、それとも周辺光量専用に別のサンプル数（20.2節推奨の1000〜100000等）を内部で使っているのかを、コードで確認する。
2. UIの「Run Charts」経由で実際に周辺光量を要求した際、何本のサンプルが使われているかを実測する。
3. サンプル数を変化させて（少数～多数）同一プリセット・同一fieldで周辺光量を複数回計算し、値のばらつき（サンプリングノイズ）を実測する。特にケラレが生じる周辺fieldで、サンプル数が結果の安定性にどれだけ影響するかを数値で示す。
4. 現状のUI既定条件（`preview`等）での周辺光量値が、十分収束した値と言えるか、ノイズが無視できないレベルかを判定する。

## 作業3：歪曲の実装確認（簡易）

1. 歪曲値が`ray_sampling`条件によらず一定であることを、複数条件での実測で簡潔に確認する（作業1と同様の手法でよい、詳細調査は不要）。

## 作業4：自動収束サンプリングの実現可能性評価（設計調査のみ、実装は対象外）

人間から「自動で、収束するまでサンプリング数を増やす方式の方が良いのでは」という提案があった。R49・R68・R70と同じ要領で、**実装せず**設計調査のみ行う。

1. 周辺光量（および該当すれば偏芯系のRMS探索方式による像面湾曲）に対して、標準誤差または逐次サンプル追加時の差分が閾値を下回るまで自動的にサンプル数を増やす、適応的サンプリング方式の実現可能性を評価する。
2. 想定される収束判定基準（相対標準誤差、逐次差分等）を1〜2案提示する。
3. 現行のRun Charts性能ガード（R71で導入した30秒以内という目安）との兼ね合いを検討する。所要時間が可変になることの影響を整理する。
4. 変更規模（小・中・大）を見積もり、推奨方針を提示する。
5. `doc/reports/issues_backlog.md`へ登録する。

## 完了条件

- 作業1：像面湾曲・M/S像面が実際にサンプル数へ依存するかどうかが、複数条件での実測値の比較で示されている。Coddington方式の使用有無がAPIレスポンスまたはコードで確認されている。
- 作業2：周辺光量が実際にどのサンプル数で計算されているか、UIの共有設定との関係が明記されている。サンプル数を変えた際の値のばらつきが数値で示されている。
- 作業3：歪曲がサンプル数に依存しないことが実測で確認されている。
- 作業4：実装は行わず、適応的サンプリングの実現可能性・規模見積もり・推奨方針が報告書とissues_backlog.mdに記録されている。
- 全作業を通じて、目視ではなく実測値・実データで結論を裏付けていること。
- 本タスクは調査のみで、コード変更は行わない（作業1〜3で明確なバグを発見した場合は、その旨を報告書に明記し、修正は別タスクとして扱う）。
