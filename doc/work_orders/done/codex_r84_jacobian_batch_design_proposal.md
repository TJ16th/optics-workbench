# R84：ヤコビアンバッチモード（engine_spec.md 25.7節）実装設計案の提案依頼（Codex向け）

**本タスクは実装ではなく、設計案の提案のみを目的とする。** これまでの指示書と異なり、完了条件は「コードが動くこと」ではなく「設計案の文書が一定の水準を満たすこと」である。

- 本タスクではproduction codeを変更しない（プロトタイプ的な検証コードを一時的に書いて動作確認すること自体は妨げないが、最終成果物はコードではなく設計提案文書であり、変更を残す場合は`git diff --check`で無関係な差分が残らないことを確認すること）。

## 背景

`doc/engine_spec.md` 25.7節「ヤコビアンバッチモード」は、外部最適化器が変数n個の有限差分ヤコビアンを計算する際、1リクエストで基準点＋n摂動点をまとめて評価し、摂動候補間でCompiledSystem・瞳サンプリング・aiming warm startを共有することで、n+1回分のコストをほぼ1回強に抑える設計として**API形状のみ**規定されている（リクエスト/レスポンスJSON形状は25.7節参照）。

R83のベンチマークで、この機能が**現状未実装**であること（`jacobian`パラメータを送ってもHTTP 200で無視される）と、実装した場合の理論効果（5変数で約4.8倍、10変数で約8.8倍、20変数で約16.8倍の短縮、保守的な`1.25×cold`仮定に基づく）を確認済みである。GPU化より投資対効果が明確なCPU側の候補と位置づけている。

**重要な制約・注意点**：R81・R82で、既存のaffine aiming cache（P0タスク4で導入）が「別条件のrequestで解いたaffine係数を別のrequestへ流用し、決定論を破壊する」バグを持っていたことが判明し、R82で「完全なrequest signature一致でのみexact solve済みoriginを再利用する」設計へ修正した。ヤコビアンバッチモードは、その定義上まさに「基準点の解を、わずかに異なる摂動configurationのwarm startへ意図的に流用する」機能であり、R81/R82で問題になったのと同じ種類のリスク（cache/warm-start流用による結果のブレ）を本質的に内包している。**この提案では、warm start流用によって最終結果が厳密解（同一配列をexact strategyで解いた場合）からどれだけ、どのような条件でズレうるかを明示し、そのズレが許容できる設計（例：warm startはあくまでNewton法の初期値としてのみ使い、必ず既定toleranceまで収束計算を行う等）を示すこと。**「速いが精度が不明」という提案は不可とする。

## 依頼内容（提案してほしいこと）

以下の論点について、コードベース（`optics_engine/tracing.py`のR82実装、`optics_engine/optimization.py`のevaluate-batch実装等）を実際に読んだ上で、具体的な設計案を提案すること。

### 1. バッチ化するtrace/aimingの構造

- 基準点＋n摂動点の全rayを1つのバッチとしてtraceする際、現行の`_trace_raw`・batch kernel（P0タスク3）・R82の exact-solve-bundle cacheとどう統合する、または並存させるかの具体案。
- 摂動点のaiming warm startとして基準点の解済みoriginをどう使うか、そしてR82の教訓を踏まえた決定論保証の具体的な仕組み（例：warm start適用後も必ず既定toleranceまでexact refinementする、等）。

### 2. 有限差分・ヤコビアン行列の計算

- forward_diff（既定）・central_diff（精度2倍・コスト2倍）それぞれの実装方針。
- 25.7節記載の変数種別ごとの既定ステップ量をどこでどう適用するか。
- 摂動後の系がハードinfeasibleになった場合の片側差分フォールバックの具体的な検出・処理方法。

### 3. API・レスポンス実装

- 25.7節のレスポンス形状（`residuals`, `matrix_shape`, `matrix`のartifact参照またはJSONインライン）をどう`/v1/optics/evaluate`へ実装するか。
- 既存の`evaluate-batch`（候補ごと独立処理、warm start共有なし）との関係整理：置き換えるのか、別機能として併存させるのか。

### 4. 精度・決定論の検証方針

- 実装した場合、バッチ化ヤコビアン結果と「n+1回を完全に独立・exact strategyで評価した場合」の結果がどの程度一致するべきか、どう検証するかの具体案（許容誤差の考え方を含む）。
- R82同様、同一requestを異なる履歴条件下で複数回実行しても結果が変わらないことを保証する回帰テスト方針。

### 5. 規模感・段階的導入案

- 実装規模を小/中/大で見積もり、根拠を示す。
- 一度に全て実装するのではなく、段階的に導入する場合のロードマップ案（R73作業6の回折MTF提案のような形式でよい）。
