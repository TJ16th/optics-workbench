# R71：Analysis Run Charts タイムアウト修正（P007/P009） 指示書（Codex向け）

## 背景

R70（`2026-07-13_r70_aberration_mtf_ui_inventory.md`）の収差図・MTF表示UI棚卸しで、P007・P009においてAnalysisタブの「Run Charts」が実用時間内に完了しないことが判明した。

- P007：実UIで300秒経過しても完了せずタイムアウト。API単体では189点中153点`alive`・36点`aiming_failed`で正常応答している。
- P009：実UIで180秒経過しても完了せずタイムアウト。API単体では189点すべて`alive`で正常応答している。

API単体は正常なため、UI側の同時実行方式（7種類の解析：Ray Fan、Longitudinal Aberration、Distortion、Field Curvature、Relative Illumination、MTF、Spot等を`full` aimingで走らせる構成）に問題がある可能性が高いと、R70報告書で分析済み（「7解析の同時実行、full aiming、個別解析の再traceを横断して計測・分離する必要がある」）。R70の優先順位案でも1位・規模「大」と評価された、今回発注する中で最も優先度の高い項目である。

## 作業

### 1. 原因の計測・特定

1. P007・P009でRun Charts実行時、UIが呼び出す各API（`/v1/analysis/ray-fan`、`/v1/analysis/longitudinal-aberration`、`/v1/analysis/distortion`、`/v1/analysis/field-curvature`、`/v1/analysis/ms-image-surface`、`/v1/analysis/mtf`、spot関連等）それぞれの個別レスポンス時間を実測する。
2. UIがこれらを直列実行しているか並列実行しているかをコードで確認する。直列実行であれば、それ自体が遅延の主要因になり得る。
3. 各APIエンドポイントが、内部で同じ光線追跡（full aiming trace）を解析ごとに重複して再計算していないか確認する。重複計算がある場合、それが最も大きなコスト要因である可能性が高い。
4. P007（`aiming_failed`が多い）・P009（非球面で1光線あたりの計算コストが高い）それぞれについて、どの要因（直列実行／trace重複／個別解析自体の計算コスト／`aiming_failed`の再試行コスト等）がタイムアウトの支配的要因かを、実測値で切り分けて特定する。
5. 目視での推測ではなく、実測（各API呼び出しのタイミングログ、プロファイリング結果等）で原因を報告書に明記する。

### 2. 【変更後】UI性能回帰テストの追加（修正ではない）

作業1の結果、R70が報告した「P007/P009でRun Chartsが実用時間内に完了しない」は製品コードの不具合ではなく、R70自身の検証スクリプトの不具合（プリセット表示名の誤指定によりPlaywrightが存在しないUIオプションを待ち続け、例外時にbrowserをcloseしなかったため外側shellタイムアウトが発火しただけ）と判明した。実測ではP007が`1078ms`、P009が`582ms`で完了しており、30秒目標を大幅にクリアしている。

したがって**製品コードの修正は行わない**。人間の判断により、作業2は以下へ内容を変更する。

1. P007・P009を対象に、Run Charts実行が実用時間内（30秒以内）に完了することを保証する**UI性能回帰テスト**を追加する。
2. プリセットの指定には、必ず作業1で確認した正しい表示名を使用する（`P007 Fast Positive-Negative Meniscus Pair 50mm Demo`、`P009 N-BK7 Aspheric Singlet 50mm Demo`）。ドロップダウンの実際のoption一覧から動的に取得する、またはコードの一次情報から取得するなど、表示名のハードコードによる将来の同種ミスを防ぐ実装を優先する。
3. テストコードは`try/finally`（またはそれに相当する確実なリソース解放構文）でPlaywright browserを必ずcloseする構造にし、例外発生時にbrowser child processが残留しない設計にする。
4. テストはRun Charts完了までの所要時間を実測し、30秒を超えた場合に明示的に失敗するアサーションを含める。
5. このテストを既存のE2Eテストスイートに組み込み、通常のCI実行対象にする。
6. 本件の顛末（R70の誤検知の原因と、その後の訂正）を`doc/ui_spec.md`または`doc/engine_spec.md`ではなく、報告書に記録する（正本仕様への影響はないため、仕様書自体の変更は不要）。

## 完了条件

- 作業1の実測結果（P007 `1078ms`、P009 `582ms`、30秒目標達成）が報告書に再掲され、製品コードには性能問題がなかったことが明記されている。
- 新規UI性能回帰テストが追加され、正しいプリセット表示名を使用していることがコードで確認できる。
- テストが`try/finally`等でbrowserを確実にcloseする構造になっていることがコードで確認できる。
- テストが30秒超過時に明示的に失敗することが、実際にテストを実行して確認されている（意図的に閾値を厳しくする等で失敗させる動作確認を行うことが望ましい）。
- 既存テストがグリーン。新規回帰テストもCIに組み込まれている。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを断定形で記載する（未来形で締めない）。
- **完了報告の実装根拠には、コミットメッセージだけでなく実際のコミットハッシュ値を必ず併記する。**
