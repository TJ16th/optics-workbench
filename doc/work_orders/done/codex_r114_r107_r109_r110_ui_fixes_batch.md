# R114＋R107/R109/R110：UI修正バッチ 指示書（Codex向け）

## 背景

Phase1〜3完了後のUI全般レビューで人間から10件の指摘を受領した（R105〜R114として台帳管理）。本指示書はうちバグ1件＋小粒3件のバッチ発注。R31で確立したバッチ実行モードを適用する：各タスクは独立、1件の失敗・中断で他を止めない。ただし**R114の調査結果が他タスクの前提を壊す発見だった場合は中断して報告**すること。

**タスク順は記載順（R114最優先）で直列に実行**すること。並行作業はR104（履歴混在事故）の教訓により禁止。コミットはタスクごとに分離し、amendは使わない（AGENTS.mdのR104追記ルール適用下）。

## タスク1（R114・最優先）：Preview上のS1/S2等ラベルの累積ずれバグ

Preview（Optical Layout）で面ラベル（S1/S2等）のレイアウトが崩れ、**下にどんどんずれていく**と人間が報告。「どんどん」という表現から、再描画・再実行のたびにオフセットが累積するバグを示唆する。

1. 再現条件を特定する（Run Previewの繰り返し／プリセット切替／凡例popover開閉／live mini-layout操作等、どの操作で累積するか）。
2. 原因を特定する。R103（compact strip化・凡例popover化・LayoutView再利用）の回帰である可能性が高いが、決め打ちせず確認すること。R28b・R41と同系統の「レイアウト変更が既存描画を壊す」パターンの再発かどうかも報告に含める。
3. 修正し、**繰り返し再描画（最低10回）後もラベル座標が安定していることをE2Eで固定**する（座標をDOM属性等で検証可能にする既存の慣行に倣う）。
4. before/afterスクリーンショットを保存する。

## タスク2（R107）：サンプル光線（density ray）のデフォルト非表示化

R27で実装済みのdensity layer切替（Show sampled rays）の**既定値をオフへ変更**する。baseline layer（chief/marginal）は従来通り既定表示のまま。

- 既定値オンを前提とする既存E2E・テストを洗い出して更新すること。
- Systemビューのlive mini-layout（R103）側の既定にも影響するか確認し、挙動を統一すること（mini-layoutは軽量表示が目的のため非表示既定が自然）。

## タスク3（R109）：ダークモードでのガラス/エア塗り分け視認性

ガラス領域の薄い塗りつぶしがダークモードで見づらいとの指摘。

1. ダークモードでのガラス/エア/接合面の塗り分けの現状コントラストを確認する。
2. ダークモード用の塗り分けtokenを調整する（R100のsemantic token基盤を使用、ハードコード追加は不可）。ライトモードの見え方は変えない。
3. ライト/ダーク両モードのスクリーンショットを保存する。R100のvisual QAで漏れた原因（ダークモードのLayout View確認が対象外だった等）も一言報告に含める。

## タスク4（R110）：スポットダイアグラムの視認性改善

R103のcompact result strip化でスポットダイアグラムが小さくなり「よく分からない」との指摘。

1. compact stripの常設表示は維持したまま、**クリック（またはボタン）で拡大表示**できる手段を追加する。拡大の形式（popover／modal／インライン拡大）はCarbonの既存パターンから適切なものをCodexが選定してよい（選定理由を報告に記載）。
2. 拡大表示では波長色・field別の判別が可能なサイズ・凡例を確保する。
3. 開閉が中央Layout寸法を変えないことをE2Eで固定する（R101/R103と同じパターン）。

## 完了条件

- タスク1〜4が各々完了し、タスクごとに独立したコミット（番号明記）が積まれている。
- 新規・更新E2Eを含め`npm run ci`全通過、`npm run ui:build:pseudo`成功。
- スクリーンショット（タスク1 before/after、タスク3 両モード、タスク4 拡大表示）を`doc/reports/screenshots/`へ保存。
- build_info一致確認（プロセス再起動・`/v1/meta`照合）。
- 数値結果・request payload・snapshotデータ構造は変更しない。i18n新規キーはja/en両方へ追加。

## 注意

- **UI側のみ。エンジン・API側は変更しない**こと。R114の原因がエンジン側と判明した場合は修正せず、その時点の調査結果を報告して指示を待つこと。
- 報告書は1本（`doc/reports/2026-07-15_r114_r107_r109_r110_ui_fixes_batch.md`、日付は完了日）にタスク別の節を設ける形でよい。着手前に全体の規模見積もり（人日換算、タスク別内訳）を報告書冒頭へ記載すること。
