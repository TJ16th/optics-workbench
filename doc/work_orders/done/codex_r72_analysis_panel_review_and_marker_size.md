# R72：Analysisタブ収差図・MTFパネルの内容精査／グラフ点サイズ修正 指示書（Codex向け）

## 背景

人間がUIを操作していて2点の違和感を報告した。

1. Analysisタブの収差図・MTF系パネル（Ray Fan、Longitudinal Aberration、Field Curvature、Distortion、MTF等、R70/R71で扱った範囲）の**表示内容が現状おかしいと感じる**。ただし具体的にどこがどうおかしいかは特定できていない（印象ベースの報告）。
2. これらのグラフの**データ点（マーカー/circle）が大きすぎて見づらい**。

1点目は印象ベースのため、まず実データ・実DOMで具体的な問題箇所を特定してから修正すること。この種の「説明文・見た目は存在するが中身が実データと食い違う」というパターンは、本プロジェクトで過去に繰り返し発生している（R33：凡例の波長色が実描画と不一致、R57：軸上主光線の非対称表示、R30-33：固定凡例と動的データの不整合等）。同種の不整合がないか、思い込みで判断せず確認すること。

## 作業1：Analysisタブ収差図・MTFパネルの内容精査と修正

1. 代表プリセット（P002：球面単玉、P003：アクロマート、P007またはP011：高速ダブルガウス、P009/P010：非球面、V001：視覚評価コンポジット）を実UIで選択し、Ray Fan・Longitudinal Aberration・Field Curvature・Distortion・MTFの各パネルを実際に表示する。
2. 各パネルについて、次の観点で実データと突き合わせて確認する。
   - 凡例（波長色、M/S、field等）が実際に描画されているデータ系列と一致しているか
   - 軸ラベル・単位（mm/µm、deg/arcmin、lp/mm/cycles/degree等）が実際の値のスケールと整合しているか
   - 表示されている数値・カーブの形状が、対応するプリセットの近軸・実光線追跡の期待値（`doc/ui_spec.md` 9.4節や既存golden test等）と矛盾しないか
   - プリセットを切り替えた際に、前のプリセットのデータやレイアウトが残留していないか（stale data）
   - `aiming_failed`を含むデータ（P007等）が、パネル上で誤解を招く形（あたかも全点が正常であるかのような表示等）になっていないか
3. 発見した不整合それぞれについて、原因（描画側のバグか、データ側のバグか、両者の接続ミスか）を特定し、修正する。
4. 修正内容と根拠（修正前後のDOM値・スクリーンショット）を報告書に明記する。**問題が見つからなかったパネルについても、確認済みである旨と根拠を明記すること**（「おかしいところはなかった」と一言で済ませず、確認した観点と結果を示す）。

## 作業2：グラフのデータ点サイズ修正

1. 現在のマーカー（circle等）のサイズを、各チャート種別（Ray Fan、Spot Diagram、Longitudinal Aberration、Distortion、Field Curvature、MTF等）について確認する。R70で確認済みの通り、例えばP002のRay Fanだけでも162個のcircleが描画されており、密集時に見づらくなっている可能性が高い。
2. データ点が密集する状況でも判別しやすいサイズへ調整する（半径縮小、透明度調整、必要であれば密集時のみ縮小する等、既存のLayout View光線描画で採用されている「半透明・細いstroke」の方針（`doc/ui_spec.md` 17.3節）も参考にしてよい）。
3. 調整後、点が少ない場合（例：Distortionのcircle2個等）に判別しにくくならないよう、サイズ調整が点数に応じて適切であることを確認する。極端に点数が異なるケース（点数の少ないDistortion／多いRay Fan等）の両方でスクリーンショットを取得し、比較する。
4. 既存のE2Eテスト（DOM上のcircle数・sectionチェック等）に影響がないか確認し、必要であれば更新する。

## 完了条件

- 作業1で発見した不整合（あれば）が、原因・修正内容・修正前後の実測値とともに報告書に明記されている。問題が見つからなかった観点についても、確認方法と結果が明記されている。
- 作業2で、データ点が密集するパネルと少ないパネルの両方でスクリーンショットを取得し、視認性が改善されたことを示している。
- 修正が既存の近軸値・実光線追跡結果・データの正しさ自体に影響を与えていないことを確認している（見た目の調整のみで、数値の意味を変えていないこと）。
- 既存テストがグリーン。DOM構造の変更に伴うE2Eテストの更新が必要であれば行っている。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを断定形で記載する（未来形で締めない）。
- **完了報告の実装根拠には、コミットメッセージだけでなく実際のコミットハッシュ値を必ず併記する。**

## 注意

- 作業1・作業2は独立した内容なので、通常規約（1タスクずつ・完了報告後に停止）に従って進めてよい。
- 「おかしいところはなかった」という結論を出す場合も、具体的にどこを何と突き合わせて確認したかを必ず示すこと（R71作業1のように、印象ベースの報告を実データで検証し直す姿勢を踏襲する）。
- R70の残りギャップ（17章View仕様欠落、white/monochromatic MTF UI未接続、aiming_failed可視化、operand未実装、diffraction included切替）は本タスクの対象外。ただし作業1の調査中にこれらと重複する具体的な不整合を発見した場合は、報告書に記録してよい（実装するかは別途判断）。
