# R116〜R119：連続作業キュー 指示書（Codex向け・無人時間帯用）

## 背景

人間が約6時間不在となるため、その間に人間の判断待ちで停止しない範囲のタスクを事前に束ねて発注する。**実行中のR105/R106調査バッチを先に完了させてから**、本キューを記載順に直列実行すること。

## キュー全体の運用ルール（重要）

1. **直列実行・タスク別コミット・amend禁止・push禁止**（R104ルール適用）。
2. **バッチ実行モード（R31）適用**：あるタスクが失敗・中断しても、そこまでの内容を報告書に書いた上で次のタスクへ進む。キュー全体を止めない。
3. **人間の判断が必要になったら、そのタスクを「提案待ち」として報告書に選択肢を書き、次へ進む**。判断を推測して実装しないこと。
4. 各タスクの報告書は個別に作成する（ファイル名は各節に記載）。着手前見積もりを各報告書冒頭へ。
5. **R105/R106の改善案・設計案の実装には着手しない**（人間の協議待ち）。

## R116：P011のfull aiming収束失敗の根本修正（エンジン）

既知backlog「P011の周辺fieldでfull aiming収束失敗を解消する」（R67導入時から存在、R80/R81で再現確認、R94で表示問題の根本原因と確定）の修正。

- 原因を特定し修正する。P011（対称6枚ダブルガウス）のedge field周辺でexact aimingが収束しない理由（初期値の質、反復上限、口径境界近傍での振動等）を実測で確認すること。
- **完了条件**：P011の全recommended fieldでbaseline ray（chief/marginal）が`aiming_failed`ゼロ。P004等、同様にaiming_failedが出る他プリセットでの改善も確認・報告（P004は11本、R114スクリーンショットで確認済み）。
- **回帰条件**：既存Golden test・エンジン全テスト・R102のビット同一テストが全て通過。aiming成功済みの光線の座標が変わる場合は、変わる理由と影響範囲（どのmetricがどの桁で変わるか）を必ず報告書に定量記載すること。R82の決定論教訓：反復回数や初期値が入力順序に依存する実装は不可。
- **修正が大規模（trace kernel本体の変更が必要等）と判明した場合**：修正せず、原因分析と修正方針案（複数、規模付き）の報告に切り替えて次のタスクへ進む。
- 報告書：`doc/reports/2026-07-15_r116_p011_full_aiming_convergence_fix.md`
