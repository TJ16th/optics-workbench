## 確認1：速度比テストのノイズ耐性

`python -m pytest` 実行時、「速度比テストが一度だけノイズで失敗し、再実行で成功した」と報告された。

1. 該当するテストファイル・テスト名を特定する。
2. そのテストが何を検証しているか（例：aperture runtime化前後の速度比、あるいは既存の別の速度比較テスト）を確認する。
3. 閾値がどう設定されているか確認する（絶対時間の閾値か、相対倍率の閾値か）。
4. CI環境（GitHub Actions Ubuntu runner）でも同様に環境負荷でフレーキーになる可能性が高いか評価する。
5. フレーキーになりやすい構造であれば、以下のいずれかで安定化する：
   - 絶対時間ではなく相対的な傾向（例：「以前よりN倍以上速い」ではなく「一定時間内に完了する」）で判定する。
   - リトライやウォームアップ実行を許容する。
   - 性能計測系のテストは通常のpytestから分離し、`bench_results/`系の計測（許容ばらつきを前提とした報告用）として扱い、pass/failを問う単体テストにはしない。
6. 対応方針と修正内容を報告する。対応不要と判断した場合はその理由を明記する。

## 確認2：iris_radius_mm variable正規化の実際の挙動

報告に「エンジンのロード時にvariable形式の数値をdefaultへ正規化している」「永続的なschema保持ではなくMVP対応」とある。この一文の意味を具体的に確認する。

1. `POST /v1/systems/register` 時、絞り面の `semi_diameter_mm: { variable: "iris_radius_mm", default: 10 }` が、CompiledSystem内でどう保持されているか（variableとしての参照が残るのか、単にdefault値10へ固定化され"variable"という情報自体は失われるのか）を、実際のコードで確認する。
2. その上で、後続の `configuration.variables.iris_radius_mm=5` が実際にtrace/preview時の瞳サンプリング・開口判定に反映される仕組みを説明する（ベンチ結果で速度が変わっている以上、何らかの形で効いているはずだが、その経路を明確にする）。
3. 現在のMVP実装で、以下のケースが正しく動くか確認する：
   - 同じsystem_idに対して、`iris_radius_mm`を送らない場合はdefault値（10）が使われる。
   - `iris_radius_mm=5`を送った場合、絞りの実効半径が5として光線が遮光される（有効径判定に反映される）。
   - 複数の異なる`iris_radius_mm`値を同一system_idに対して連続で送った場合、前回の値が残留しない（真にステートレスである）ことを確認する。
4. 上記が未検証であれば、簡単なテスト（例：iris_radius_mm=3の遮光結果とiris_radius_mm=8の遮光結果が異なることを確認するテスト）を追加する。
5. 「永続的なschema保持ではない」という制約が、将来他のvariable（S1_curvature等、25.6節の変数キー）にも同じ方式を広げる際の障害にならないか、簡単に見解を報告する（詳細設計は不要、懸念があれば一言でよい）。
