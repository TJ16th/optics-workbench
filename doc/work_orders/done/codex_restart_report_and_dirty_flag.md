# 完了報告ファイルの作成（再依頼）とgit_dirty挙動の記録

## 背景

直前のプロセス再起動作業の結果はチャット上のテキストとして報告されたが、`doc/reports/`への完了報告ファイルとしては見当たらない。AGENTS.mdの「実装報告は`doc/reports/`に`YYYY-MM-DD_<件名>.md`形式で追加する」に従い、ファイルとして残す。

また、確認結果の中で`git_dirty=True`の理由が「`doc/work_orders/active/`配下の指示書ファイルが未追跡だったため」と分かった。これは実害はないが、今後も指示書を追加するたびに`git_dirty=True`が常態化しうるという弱点を示している。

## 作業

1. `doc/reports/2026-07-10_restart_processes.md`として、直前にチャットで報告した内容（旧PID、起動コマンド、新PID、build_info確認結果、education/preview確認結果）をそのまま記録する。
2. `git_dirty`の意味づけを見直す。以下のいずれかで対応する（判断して報告する）：
   - (a) `git_dirty`の算出対象から`doc/`配下（指示書・報告書）を除外し、コード（`optics_engine/`、`apps/`等）の変更のみを見るようにする。
   - (b) 対応せず、「`git_dirty`はdoc/work_ordersの追加でも真になる」という制約をAGENTS.mdまたはbuild_infoのドキュメントに一言明記するだけに留める。
   - どちらを選ぶか、理由とともに報告する。過剰な作り込みは不要（本筋の性能・機能タスクを止めてまで対応する優先度ではない）。
3. 今後、Codexが人間からの簡易な確認依頼（今回のような再起動作業等）に対応した場合、その内容が実装報告に値するかどうかの判断基準を確認する：AGENTS.mdの「実装報告は`doc/reports/`に追加する」は、コード変更を伴わない運用作業（プロセス再起動、環境確認等）にも適用されるべきか、一言見解を報告する。曖昧であれば、AGENTS.mdに「コード変更を伴わない確認・運用作業であっても、人間から明示的に依頼された調査・確認タスクは完了報告を`doc/reports/`に残す」旨を追記する。

## 完了条件

- `doc/reports/2026-07-10_restart_processes.md`が存在する。
- `git_dirty`の対応方針（(a)または(b)）が実施・記録されている。
- AGENTS.mdへの運用作業の報告義務に関する追記が完了している（または不要と判断した理由が報告されている）。
