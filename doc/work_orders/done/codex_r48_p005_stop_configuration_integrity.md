# R48：P005の絞り構成の設計整合性確認（STOP種別・重複マーカー） 指示書（Codex向け）

## 背景

R45完了後、人間が実際のスクリーンショットを確認したところ、Layout View上に「STOP」（塗りつぶし丸）と「Annulus STOP（副鏡による中央遮蔽）」（輪郭丸）が、ほぼ同じX座標に2つの別マーカーとして描かれていることに気づいた。エンジン仕様6.4節では「開口絞りは系にちょうど1つ」と定義されており、これが2つの独立した絞り面として存在しているなら仕様と矛盾する。

また、人間から「カセグレン式のようなミラー系望遠鏡では、絞り（主鏡の有効径）は通常固定であり、可変絞りにする光学的な必然性がない」という指摘があった。現在P005のSTOP面は`kind: aperture_stop`（可変絞り）として実装されているが、これはR41（絞り種別依存の座標計算バグの修正）の際に、座標計算上の理由で選ばれたものであり、光学的な妥当性の観点では検討されていなかった可能性がある。

## 作業

### 1. 絞り構成の客観的な確認（最優先）

1. P005のsystem定義における面構成を再度確認し、「STOP」と表示されているマーカーと「Annulus STOP」と表示されているマーカーが、実際には同一の面（1つのannulus絞り面）を指しているのか、それとも本当に2つの独立した面（絞り面が2つ存在する仕様違反状態）なのかを確定する。
2. 1つの面であるにも関わらず2つのマーカーとして描画されている場合、Layout View描画コードのどこで重複描画が発生しているか特定する（STOP用の描画ロジックとAnnulus STOP用の描画ロジックが、それぞれ独立に同じ面を対象として動いている可能性が高い）。
3. 本当に2つの絞り面が存在する場合（`kind: aperture_stop`の面と、別の`kind: mechanical_aperture`または`aperture_stop`のannulus面が両方定義されている場合）、これは仕様6.4節（開口絞りは1つ）への違反であることを報告する。

### 2. 絞り種別（aperture_stop vs mechanical_aperture）の妥当性判断

1. 実際のカセグレン式望遠鏡の設計慣行を踏まえ、主鏡の開口絞りが可変（`aperture_stop`）であるべきか、固定（`mechanical_aperture`）であるべきかを判断する。一般的な望遠鏡は固定絞りが標準的であることを踏まえる。
2. R41で`kind: aperture_stop`に変更した経緯（座標計算バグの回避）を確認し、その変更が「座標計算上必要だったから」なのか、「`mechanical_aperture`では原理的に実現できないから」なのかを切り分ける。もし後者の場合、その制約自体が別のバグである可能性があるため、原因を確認する。
3. 座標計算のロジックが絞り種別に依存すること自体が設計上の弱点であるなら（R41の教訓）、`mechanical_aperture`でも正しく座標計算できるよう根本的に修正することを検討する。過剰な作り込みは避け、まずは現状の制約を正確に報告することを優先する。
4. 対応方針を判断し報告する：
   - (a) 座標計算の制約が解消できるなら、P005のSTOP面を`mechanical_aperture`（固定）に変更する。
   - (b) 制約が解消できない、または他に優先すべき理由があれば、`aperture_stop`のまま維持し、その理由を明記する（ユーザーが誤って絞り半径を変更できてしまうことの影響も評価する）。

### 3. annulus絞りの正しい単一面としての整理

1. 作業1で「1面のはずが2マーカーとして重複描画されている」と判明した場合、Layout View描画を修正し、annulus絞りを1つの一貫したマーカー（annulus形状であることが視覚的に分かる、例えば輪郭丸のみ、または塗りつぶしと輪郭を組み合わせた1つの表現）として描画する。
2. 凡例も、重複していた「STOP」と「Annulus STOP」の2項目を、実態に応じて1項目に整理する（annulus絞りは常にAnnulus STOPとして表示し、通常の円形絞りはSTOPとして表示する、という単純な使い分けであれば、2項目のままでも問題ない。ただし同一面が両方の見た目を持つことは無いようにする）。

## 完了条件

- STOP/Annulus STOPマーカーが同一面か別面かが確定し、重複描画があれば解消されている。
- 絞り種別（aperture_stop/mechanical_aperture）の妥当性判断が報告され、対応方針が実施されている。
- 修正後のLayout Viewスクリーンショットが`doc/reports/screenshots/`配下に保存され、完了報告から参照される（R46規約に従う）。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを確認し、断定形で報告に記載する（未来形で締めない）。
