# R66：P005非表示化／有効径の全プリセット再点検／ダブルガウス50mm F1.4プリセット新設 指示書（Codex向け）

## 背景

R61で人間が「反射系（P005カセグレン）はいったん封印」と判断した際は、**台帳記録のみに留め、UI・ドキュメントへの反映は行わない**方針だった。今回、人間の方針が一歩進み、**P005を通常のプリセット一覧から実際に非表示にしたい**という要望になった。対象はP005（カセグレン、実際にミラーを使う唯一の系）のみ。P006（Keplerian Telescope）は`thin_lens`のみで構成されミラーを使わないafocal系であり、R54〜R61の一連の問題（annulus、STOP、多重反射の懸念等）はすべてP005固有のものだったため、P006は対象外とする。

また、R29（`2026-07-11_r29_preset_semi_diameter_review.md`）でP001〜P003・P007の有効径（semi_diameter）を実marginal ray高さ+10〜12%マージンへ調整した後、R62・R63・R64で新規プリセットP007（再設計）・P008・P009・P010が追加・変更されたが、これらはR29のような有効径過剰チェックを経ていない。人間から「有効径が過剰になっている箇所が散見される」との指摘があり、改めて全プリセットを点検する必要がある。

最後に、人間から「ダブルガウス50mm F1.4のプリセットが欲しい」という要望があった。`doc/ui_spec.md` 9.4節にはP004「Simplified Double Gauss 50mm Demo」という設計例が記載されているが（8面+STOP構成）、R65で確認済みの通り**この設計は実コードに一度も実装されていない**。この設計例のR/D値はEFL・F値の近軸検証を経ておらず、記載されている数値が実際にF1.4付近を達成するかどうかは未確認である。

## 作業1：P005を通常のプリセット一覧から非表示にする

1. P005の定義（`presets.ts`等）自体は削除しない。エンジンAPI・バックエンド・既存テスト（`test_preset_api_smoke.py`はpresets.tsを動的読み込みしてカバレッジを取る設計であるため、配列から物理的に取り除くとテストカバレッジが失われる点に注意）からは引き続き参照・利用できる状態を維持すること。
2. UIのプリセット選択リスト（通常操作で選べるドロップダウン等）からP005だけが選べなくなるようにする。実装方法はCodexの判断に委ねるが、例えば各プリセット定義に`visible: false`のようなフラグを追加し、UI側のリスト生成箇所でフィルタする、といった「データは残すが表示だけ除外する」形が望ましい。既存の`?fixture=asphere-layout`のような隠しURLパラメータ経由でのアクセス可否は必須要件ではないが、実装が容易であれば残してよい。
3. 非表示化がAPI・golden test・`test_preset_api_smoke.py`等の既存カバレッジに影響しないことを確認する（P005関連のテストが黙って消えていないか確認すること）。
4. `doc/ui_spec.md`のプリセット一覧・件数記載（9.1節等）を、「UIに表示される代表プリセット数」と「内蔵プリセット総数」が区別できるように更新する。P005の定義自体（9.4節の記載）は削除せず、「UI非表示」である旨を明記する程度でよい。

## 作業2：全プリセットの有効径（semi_diameter）再点検

1. 現時点で実コードに存在する全プリセット（作業1で非表示化されたP005も含めてよい。非表示でも定義は残るため）を対象に、R29と同じ方法論（各面での実marginal ray到達高さを実際にトレースして求め、+10〜12%程度のマージンを載せた値に丸める）で有効径（semi_diameter）が過剰でないか点検する。
2. 特に、R29のチェックを経ていないP007（R63で再設計済みの現行版）・P008・P009・P010を重点的に確認する。P001〜P003もR29以降に変更がないか確認し、変更があれば再点検する。
3. 過剰と判定した面があれば、R29と同じ要領で実測値に基づき修正する。P005・P006については、R29で「瞳・遮蔽条件を構成する特殊面のため意図的に現状維持」と判断された理由が今回も妥当か確認し、妥当であれば踏襲、そうでなければ理由を明記した上で判断を更新する。
4. 修正を行った場合は、修正前後の値・実測根拠（marginal ray高さ）を報告書に明記し、近軸検証値（EFL・F値等）に影響がないことを確認する。
5. `doc/ui_spec.md` 9.4節の該当プリセットの面データ記載も、実コードと一致するよう更新する。

## 作業3：ダブルガウス50mm F1.4相当プリセットの新設（P004を正式実装）

1. `doc/ui_spec.md` 9.4節に記載されている未実装のP004設計例（8面+STOP、対称型ダブルガウス構成）を出発点とし、まず近軸計算でEFL・F値を確認する。
2. 記載値がF1.4付近（目安：F1.4〜F2.0程度、要求は「50mm F1.4」だが、既存記載値が大きく外れる場合はR63と同様の手順——物理的に正しい形状（エッジ厚が正であること等）を保ちながら近軸目標に近づける再設計——を行う。再設計する場合は変更点と根拠を報告書に明記すること。
3. 最終的な設計をP004として正式にコードへ実装する（現在コード上の最終番号がP010であることは確認済みだが、番号の欠番であるP004を埋める形で採番する。念のため実装前に現在のプリセット一覧をコードで再確認すること）。
4. 作業2の有効径方法論（実marginal ray高さ+10〜12%マージン）を設計段階から直接適用し、後から過剰判定を受けないようにする。
5. 近軸トレースと実光線追跡の両方で検証し、EFL・F値・BFL・center/mid/edge fieldでの実光線到達率（alive数）を報告書に数値で明記する。全fieldで無遮光（blocked 0）であることが望ましいが、そうならない場合は理由と数値を明記する。
6. spot diagram・MTF・distortion・field curvatureが表示可能なことを確認し、可能であればP002等との球面収差比較かspot RMSの数値を示す。
7. Layout Viewのスクリーンショットを取得する。
8. `doc/ui_spec.md` 9.1/9.4節にP004の実装済み面データ・検証値を反映し、プリセット総数・番号の連続性を更新する。

## 完了条件

- P005が通常のUIプリセット一覧から選べなくなっている一方、定義・API・既存テストカバレッジは維持されていることが実際の操作・DOM確認で示されている。
- 全プリセットの有効径点検が実施され、点検方法（marginal ray実測値）と判定結果（修正の有無）が報告書に数値で明記されている。修正を行った面があれば修正前後の値が明記されている。
- P004が実コードに実装され、近軸・実光線追跡の両方でEFL・F値等の数値が報告書に明記されている。F1.4という目標に対する達成度（一致／近似／未達とその理由）が明確に述べられている。
- 3作業とも`doc/ui_spec.md`が実コードと一致するよう更新されている。
- 既存テストがグリーン。新規プリセット追加・既存プリセット変更に伴う回帰（自然順テスト、golden test等）も確認する。
- 完了報告前にプロセスを再起動し、`build_info.git_commit`がHEADと一致することを断定形で記載する（未来形で締めない）。
- **完了報告の実装根拠には、コミットメッセージだけでなく実際のコミットハッシュ値を必ず併記する。**

## 注意

- 作業1・作業2・作業3は内容が独立しているため、通常規約（1タスクずつ・完了報告後に停止）に従って進めてよい。ただし作業3は作業2の有効径方法論を前提にするため、作業2を先に完了させてから着手することを推奨する。
- 「有効径が過剰」「F1.4を達成した」等の主張は、目視ではなく必ず実測・数値（marginal ray高さ、近軸計算、実光線追跡結果）で裏付けること。
- P005非表示化はデータの削除ではない。既存の反射系サポート自体（engine_spec.md）は変更しない（R61の方針を継続）。
