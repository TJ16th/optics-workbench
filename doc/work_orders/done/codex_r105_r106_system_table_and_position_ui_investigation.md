# R105/R106：諸元表の実態調査＋ポジションUIの棚卸し・設計提案 指示書（Codex向け）

## 背景

Phase1〜3完了後のUIレビューで人間から受領した指摘のうち、調査が先行すべき2件。**本タスクは調査・提案のみで、製品コードの変更は行わない**（R70/R99と同じ扱い）。バッチ実行モード適用、記載順に直列実行。

## タスク1（R105）：Systemの諸元表が一望できない・編集できない

人間の指摘：「諸元表が一望できない。表は横長なのに表示域が足りない」「諸元表を編集できない」。

1. **表示域の実態確認**：1920×1080で代表プリセット（列数が多いP004またはP011、非球面列があるP009/P010）を開き、surface tableの全列（ID/Kind/Surface/Radius/Asphere/Thickness/Material/Semi-Diameter等）のうち何列が見え、何列が隠れる（横スクロール発生）かを実測する。R103のlive mini-layout併設が表の幅をどれだけ圧迫しているかも定量化する（mini-layoutなしの場合の表示可能列数との比較）。
2. **編集可否の実態確認**：surface tableの各列について「編集UIの有無／編集の反映先（preview即時か、register要求か）」の一覧表を作る。R103完了報告は「surface編集後は70ms debounceでpreviewを更新」としているが、人間は「編集できない」と認識している。この食い違いの原因を特定すること（例：編集可能な列が一部だけ／編集UIの見た目が読み取り専用に見える／特定のkindの面だけ編集可能、等）。
3. **改善案の提示**：1と2の結果を踏まえ、改善案を複数提示し推奨を1つ選ぶ。観点：列の優先順位付け・折りたたみ、mini-layoutの一時収納、全幅表示モード、編集可能領域の視覚的明示、R4（Raw JSON/YAML editor、backlog登録済み）との役割分担。実装規模（小/中/大）を各案に付けること。

## タスク2（R106）：ズーム/フォーカス/OISポジションの登録・確認UI

人間の指摘：「ズームフォーカスOISポジションの登録・確認画面がない？システム内で定義するのがいいのか？」

1. **現状棚卸し**：
   - engine_spec 10.2節のnamed zoom_positionsについて、エンジン側の実装状況（system定義での受理、configuration切替、`/v1`各endpointでの参照可否）を確認する。
   - UI側の現状：Zoom Group定義UI（P3-1）、Group Motionスライダー（P3-2、ズーム・フォーカス・OISシフト）はあるが、named positionの登録・一覧・切替UIが存在するかを確認する。
   - プリセット側：フォーカス群付きプリセット（R98のP013等）がzoom_positionsをどう持っているか確認する。
2. **設計提案**：named position（例：wide/tele、無限遠/至近、OISシフト点）を「どこで定義し、どこで登録・確認・切替するか」の設計案を複数提示し、推奨を1つ選ぶ。論点：
   - system定義内（persistent、export対象）かUI状態（セッション限り）か、その中間（プリセットは定義済み・UIから追加登録可）か。
   - Group Motionスライダーとの関係（スライダー現在値を「この位置をwideとして登録」的に保存する導線等）。
   - R5（multi-configuration最適化）・R6（ズーム軌跡最適化）の将来要件と矛盾しない設計であること。**実装はしないが、この2件の仕様検討の土台になる粒度で書くこと**（R84の設計提案方式と同じ扱い）。
   - 各案に実装規模（エンジン変更の要否を含む）を付けること。
