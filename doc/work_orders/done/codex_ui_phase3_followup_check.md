# P3進行確認：曲率描画・aperture実装の確認事項（差し替え版）

## 確認1：曲率描画修正（`codex_ui_layout_curvature_fix.md`）の状況【最優先】

事実関係：`codex_ui_layout_curvature_fix.md` をP3-2より先に対応するよう依頼していたが、実際にはP3-2〜P3-5が先に実行され、曲率描画修正はまだ着手されていない。つまり**Group Motion / Aperture / Decenter-Tiltの各パネルは、面が直線描画のままのLayout View上に実装された可能性が高い**。

1. まず現状のLayout Viewのスクリーンショットを、P002（単純な単レンズ）とP003（現在拡張済みのアクロマート＋群構成）の両方で提示する。面が曲率に応じた弧で描かれているか、直線のままかを確認する。
2. 直線のままであれば、`codex_ui_layout_curvature_fix.md` の指示内容（原因調査→エンジン/UIどちらの改修か切り分け→修正→凸/凹の符号確認→非球面sagカーブ確認）に**このタスクとして今すぐ着手する**。P3-6（Phase 3受け入れ確認）より前に完了させる。
3. 曲率描画が未修正のままP3-2〜P3-5で追加したスライダー操作（group shift、aperture、decenter/tilt）の**見た目上の実害**があるかも報告する。具体的には：
   - decenter/tiltで面が視覚的に区別されるという報告（破線・太線・赤マーカー）は、面自体が直線描画のままでも成立する表現なので実害は小さい可能性がある。
   - 一方、absolute値としての「曲率が変わる操作」（もしあれば）や、非球面プリセットでの表示は、直線描画のままだと変化が全く見えない可能性がある。P3-2〜P3-5の対象操作（group shift, aperture, decenter, tilt）はいずれも面の曲率自体は変えない操作なので、直線描画のままでも「動きは見える」状態だった可能性はある。この点を実際の画面で確認し、報告する。

## 確認2：Aperture操作のsystem再登録をruntime configuration化する

P3-3の実装は、絞り半径変更のたびに `aperture_stop.semi_diameter_mm` を更新した一時systemを新規登録している。これによりP3-5の計測で、aperture操作がgroup shift操作（5〜10ms）やdecenter/tilt操作（約19ms）より重い約30msになっている（system再登録のオーバーヘッドとCompiledSystemキャッシュの不成立が原因と推測される）。

エンジン仕様19.3節では、可動絞り（`aperture_stop`）の半径は `iris_radius_mm` という**ランタイムのvariable**として、system構造を変えずに送れる設計になっている（`variable: iris_radius_mm` 形式で面定義済みの場合）。

- 対象プリセット（P003等）の絞り面定義が `semi_diameter_mm: { variable: iris_radius_mm, default: ... }` 形式になっているか確認する。
- なっていれば、P3-3の実装をsystem再登録方式から、`configuration.variables.iris_radius_mm` を送るランタイム方式へ変更する（P3-2のgroup shiftと同じ「既存登録済みsystemを使う」経路に揃える）。
- なっていなければ、まず対象プリセットの絞り面定義をvariable形式に直してから、同様にUI実装を変更する。
- 変更後、P3-5と同条件でaperture操作のレイテンシを再計測し、改善幅を報告する。
