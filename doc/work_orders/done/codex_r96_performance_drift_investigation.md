# R96：R82以降のspec-like smoke性能ドリフト調査 指示書（Codex向け）

## 背景

R93完了報告で、spec-like smoke benchmarkをR82時点（`bench_results/20260714_132336_33457c8.json`）とR93完了時点（`bench_results/20260715_000607_222f6ad.json`）で比較すると、`preview full`が+24.2%、`high-count trace`が+3.9%、`fast_design_score`が+88.0%増加していたことが報告された。この間にはR83〜R93の多数のコミットが介在するため、R93単独の影響とは断定できないとCodex自身が正直に注記していた。

本タスクは、この性能ドリフトがどのコミット・どの変更に起因するかを特定し、意図した機能追加による正当な増加なのか、意図しない非効率が紛れ込んだものなのかを判定する。

## 作業

1. R82時点（`33457c8`）から現行HEADまでの主要コミット（R87変数バインディング・指標接続、R88入力検証強化、R89-1 ray_loss_ratio・seed、R89-2専用瞳サンプリング、R89-3 edge_thickness/constraint、R89-4近軸像距離solve、R90 merit統一、R91 Jacobian J2/J3、R93 candidate軸kernel等）の各時点で、同じspec-like smoke benchmark（`preview full`・`high-count trace`・`fast_design_score`を含む既存のbenchmark profile）を実行し、どのコミットで増加が発生したかを特定する。
2. 特に`fast_design_score`の+88.0%という大きな増加に注目する。R89-1（ray_loss_ratio疑似operandの自動追加）やR90（merit統一・derivation関数の一本化）が候補として疑わしいが、決め打ちせず実測で確認すること。
3. `preview full`の+24.2%についても、R87の指標接続やR89-2の専用瞳サンプリング実装（gaussian_quadrature等の実装により、既定gridパスも共通コード経路が重くなっていないか）が候補になりうるが、同様に実測で確認する。
4. 増加の原因が判明したら、それが「正しさのために必要なコスト」（例：ray_loss_ratioは25.5節の必須契約であり、計算しないわけにはいかない）なのか、「最適化の余地がある非効率」（例：不要な再計算、キャッシュされるべき値の毎回計算等）なのかを判定する。
5. 最適化の余地がある場合、その修正規模（小/中/大）を見積もる。本タスクでは修正は行わない。

## 完了条件

- `preview full`・`high-count trace`・`fast_design_score`それぞれの増加が、どのコミット（複数の場合は内訳）に起因するかが実測で特定されている。
- 各増加が「正しさのための必要コスト」か「最適化の余地がある非効率」かが判定され、根拠が示されている。
- 現在の絶対値が、R71等で設定された既存の性能ガード（30秒等）に照らして問題ないかどうかも確認されている。
- 最適化の余地がある場合、修正方針・規模感が報告書に記載されている（実装はしない）。
- 本タスクは調査のみであり、コード修正は行わない。

## 注意

- 「このコミットが原因」という結論は、推測ではなく実際にそのコミット時点でbenchmarkを再実行した実測値で裏付けること。
- 複数の要因が積み重なっている可能性があるため、単一コミットに原因を絞れない場合はその旨を正直に報告すること。
