# 光学エンジン 性能改善 作業指示書（Codex向け）

## 進め方（必読）

- タスクは**必ず番号順に、1タスクずつ**実施する。タスクを飛ばさない。並行して進めない。
- 各タスクの完了時に、変更ファイル一覧・テスト結果・計測結果を報告し、**次のタスクに進む前に停止する**。
- ベンチマーク結果に基づく前回分析の結論：現状のボトルネックは ray aiming 単体ではなく、**per-rayのPythonトレースカーネル（約1ms/トレース、70µs/面・本）を aiming が約10倍に増幅している**構造である。したがって改善の本丸はタスク3のバッチ配列化であり、瞳アフィン写像はその後に実装する。

## 共通制約（全タスクに適用）

1. 既存の36本のテストは常にグリーンを維持する。
2. 現在の per-ray トレース実装は**削除しない**。`optics_engine/reference/` 等へ移動し、Level 0 リファレンス実装として保持する（仕様27.4節：Level 0は「常に保持（Golden Testの基準）」）。
3. 新しいカーネルコードは仕様27.5節の規律に従う：純関数（グローバル状態・in-place副作用なし）、データ依存分岐はマスク演算（np.where）で表現、遮光・失敗は配列削除ではなく weight=0 / statusマスク（配列shape不変）、反復は固定回数上限＋収束マスク方式。
4. 公開APIのシグネチャ（evaluate、trace系の入出力スキーマ）は変更しない。
5. 各タスクは独立したコミット（またはPR）とし、コミットメッセージにタスク番号を含める。

## タスク0：計測基盤の修正と切り分け実験（コード変更はベンチのみ）

### 目的

投資判断の前に、ボトルネックがカーネル単価にあることを実測で確定する。

### 作業

1. `benchmarks/spec_like_benchmark.py` を以下のとおり修正する。
   - repeat を 5以上にし、初回1〜2回を warmup として統計から除外する。median と p95 を報告する。
   - **全ケースで総光線数・fieldごとの角度設定をログに含める**（evaluateケースも含む）。光線1本あたり・1面あたりのコストを自動算出して出力する。
   - relative illumination ケースに理論チェックを追加する：最外field角 θ に対する cos^4(θ) の理論値を併記し、実測RIとの比を出力する。field角が±15°以上になるようベンチのfield設定を明記・調整する（現状の min RI 0.9849 は field角が小さすぎるか cos^4 が効いていない可能性がある。どちらかを特定して報告する）。
2. 同一の合成14面系ベンチを `ray_aiming: full` / `paraxial` / `off` の3条件で実行し、比較表を出す。
3. **ベンチ結果の履歴化と推移レポート**を実装する。
   - ベンチ実行のたびに、結果を `bench_results/{日時}_{git短縮ハッシュ}.json` として保存する（profile名、全ケースのmedian/p95、総光線数、per-ray cost、環境情報を含む機械可読形式）。
   - `benchmarks/report.py` を新設し、`bench_results/` 内の全JSONからケース別の時系列推移グラフ（matplotlib）を含む静的HTML 1ファイルを生成する。サーバー・ビルドシステム・外部JSは使わない。
   - 以後の全タスクの完了報告では、このJSONへの追記と「前回計測比の変化率」の記載を必須とする。

### 完了条件

- 3条件の比較表（median / p95 / per-ray cost / per-surface-ray cost）が出力される。
- `bench_results/` に初回計測JSONがコミットされ、report.py が静的HTMLを生成できる。
- `off` 条件でのトレース単価（ms/ray）が報告される。この値が ~1ms/ray 級であれば「カーネル単価が支配的」の確定として報告する。
- RI の cos^4 突き合わせ結果と、乖離があればその原因の特定結果を報告する。

### 禁止事項

- このタスクではエンジン本体のコードを変更しない。

## タスク1：最小Golden Test（書き換え前の保険）

### 目的

タスク3でカーネルを全面書き換えする前に、数値の正しさを固定する回帰網を張る。符号規約バグ（曲率・厚み・角度の符号）は既存の単体テストでは捕まらない。

### 作業

`tests/golden/` を新設し、以下の2系統×2階層のテストを実装する。

**系1：アクロマートダブレット（UI仕様 P003 相当）**

```yaml
# 面: R=61.47 (N-BK7, t=7.5) / R=-44.64 (N-F2, t=3.0) / R=-129.94 (AIR)
# 絞り: 第1面の5mm手前, semi_diameter 12.5
# 波長: 486.13 / 587.56 / 656.27 nm
```

**系2：カセグレン（エンジン仕様v2.1 6.3節の検証済み数値）**

```yaml
# M1: R=-2000, thickness_after=-650, semiD=100
# M2: R=-1050, thickness_after=+1050, semiD=40
```

**階層A：物理サニティ（緩い許容差、手計算・理論値との比較）**

- カセグレン近軸（厳密な手計算値が既知）：
  - EFL = 3000 mm（相対誤差 1e-6 以内）
  - 像位置 = M2 の 1050 mm 後方（同上）
  - 口径半径100mmのマージナル光線の M2 到達高 = 35 mm（同上）
- ダブレット：EFL が 95〜105 mm の範囲、F線とC線の近軸焦点位置差（軸上色収差）が d線EFLの 0.1% 未満（アクロマート条件の確認）。

**階層B：凍結回帰（厳しい許容差）**

- 階層Aが通った時点の実測値（EFL、BFL、代表光線のセンサー到達座標、軸上spot RMS）をJSONに凍結保存し、以後は相対誤差 1e-9 で一致を要求する。
- 凍結値を更新する場合は、テスト内のコメントに更新理由を必須記載とする。

### 完了条件

- 階層A・Bの全テストがグリーン。
- 凍結JSONがリポジトリにコミットされている。
- 既存36テスト＋Goldenテストの合計がグリーン。

### 目的

安価で即効性のある改善。paths（全経路記録）を生成せずに、stop面到達点のみを返す。

2. ray aiming の残差計算（Newton反復内の途中トレース）を、この関数を使うように置き換える。
3. タスク0のベンチ（full aiming 3条件比較）を再実行し、before/after を報告する。

### 完了条件

- 全テスト（Golden含む）グリーン。
- full aiming ベンチが改善している（目安：2倍以上）。改善幅と、per-ray costの内訳変化を報告する。

## タスク3：バッチ配列トレースカーネル（本丸・最重要）

### 目的

仕様27.4節 Level 1。トレース単価を per-ray ~1ms から配列一括処理へ置き換え、性能目標達成の主手段とする。

### 作業

1. **CompiledSystem を構造化配列に落とす**（仕様27.4節の配列レイアウトに従う）：

```
surface_type:      int8[n_surf]
curvature:         float64[n_surf]
conic:             float64[n_surf]
asphere_coeffs:    float64[n_surf, max_order]
semi_diameter:     float64[n_surf]
inner_diameter:    float64[n_surf]      # annulus用
n_before / n_after: float64[n_surf, n_wavelengths]
local_transform / inverse_transform: float64[n_surf, 4, 4]
propagation_sign:  int8[n_surf]
```

2. **バッチカーネルを実装する**。光線群を `origins [N,3]`, `directions [N,3]`, `wavelength_index [N]`, `status [N]`, `weight [N]` で持ち、面ループの内側で全光線を一括処理する：

```
for surface in surfaces:
    ローカル変換（[N,3]一括）
    交点計算（球面・平面は閉形式を一括。非球面はNewtonを固定上限＋収束マスクで一括）
    有効径・annulus判定（マスク更新、光線は削除しない）
    法線計算・屈折/反射/薄レンズ（np.whereで分岐）
    グローバル変換
```

3. **等価性テストを追加する**：Golden Test の2系＋非球面を含むベンチ14面系について、Level 0（reference実装）と Level 1 のセンサー到達座標を全光線で比較する。許容差は球面のみの系で atol=1e-9 mm、非球面を含む系で atol=1e-8 mm。
4. **aiming のバッチ化**：Newton反復を「全 field × 波長の主光線をまとめた配列」に対して一括実行する（収束済み光線はマスクで凍結し、全収束または上限で終了）。ヤコビアンの差分トレースも同一バッチに含めてよい。
5. 既存の解析関数（spot、RI、PSF等）の呼び出し経路をバッチカーネルに切り替える。per-ray 実装は reference として温存する。

### 完了条件

- 全テスト（既存＋Golden＋等価性）グリーン。
- ベンチ：**14面系・1万本・aiming off のトレースが 200 ms 以内**（目標 50 ms 以内）。
- タスク0と同一条件の spec_like_benchmark を再実行し、全ケースの before/after 表を報告する。
- 教育preview（3 field × 1λ × 25 rays、paraxial aiming、ライブラリ直呼び）が 100 ms 以内。

### 注意

- このタスクが最大の書き換えである。**Golden Test（タスク1）が未完なら着手しない。**
- Numba はこのタスクでは使わない（純NumPyで完了条件を満たすこと。Numbaはタスク6で非球面Newtonに限定適用する）。

## タスク4：瞳アフィン写像とwarm startキャッシュ

### 目的

仕様16.3節。厳密aimingを主光線＋絞り縁サンプルに限定し、中間瞳点をアフィン近似で生成する。

### 作業

1. field×波長ごとに、主光線＋絞り縁4点（decenter/tilt存在時は8点）を厳密aimingし、絞り面上の実効瞳のアフィン写像（中心＋楕円）を構築する。
2. 中間の正規化瞳座標はアフィン写像で生成する。解析モードでは、生成光線の絞り面到達誤差が閾値（既定：絞り半径の1%）を超える光線のみ個別に追加反復する。previewモードでは追加反復を省略する。
3. aiming解キャッシュを実装する。キー：`system_hash + configuration_hash + field + wavelength + stop半径`。配置パラメータ変更時は該当fieldのみ無効化し、前回解をNewtonの初期値（warm start）に使う。
4. 検証テスト：アフィン近似で生成した光線束の絞り面充填の一様性（到達点の重心ずれ・被覆率）を、全点厳密aimingと比較するテストを追加する。

### 完了条件

- 全テストグリーン。
- spec_like_benchmark で仕様27.3節の目標に対する達成状況を表で報告する。最低ライン：
  - Spot簡易解析（5 field × 3λ × 512 rays）: 1 秒以内
  - 最適化粗評価（evaluate fast_design_score）: 500 ms 以内
- warm start の有無で aiming 反復回数がどう変わるかを計測して報告する。

## タスク6：インタラクティブ性能検証用の使い捨てレイテンシハーネス

### 目的

仕様27.3節の「絞り・群移動の連続操作で10 fps程度」は、ベンチスクリプトでは検証できない（HTTP往復・シリアライズ・連続リクエスト時の詰まりは実操作ループでしか見えない）。これを計測する最小ハーネスを作る。

### 作業

1. `benchmarks/latency_harness.html` を**単一HTMLファイル**として作成する。
   - 絞り半径スライダーと群shift_xスライダーを置き、変更のたびに `POST /v1/education/preview`（system_id参照、aiming: paraxial、25 rays × 3 fields）を送信する。
   - 直近リクエストのend-to-endレイテンシ（ms）、直近1秒の実効fps、profiling metadata（タスク5）の段階別内訳を画面に数値表示する。
   - 応答が返る前に次のスライダー変更が起きた場合の制御（in-flight中は最新値のみ保持し、応答後に送信）を入れ、詰まりの有無を可視化する。
2. 実装上の制約（**スコープ肥大の禁止**）：
   - ビルドシステム・npm・フレームワーク・外部JSライブラリを使わない。素のfetchとDOM操作のみ。目安200行以内。
   - 光線図などの描画はしない。数値表示のみ（レイテンシ計測に描画コストを混ぜない）。
   - これはWorkbench UI（別仕様）の先行実装ではない。使い捨て計測治具であり、機能追加やデザイン調整を行わない。
3. エンジン側にCORS許可の起動オプションがなければ追加する（開発用途、既定off）。
4. スライダーを10秒間連続操作したときの実効fpsと、profiling内訳（どの段階が支配的か）を計測して報告する。

### 完了条件

- ハーネスがブラウザで動作し、連続操作時の実効fpsが計測・報告される。
- 10 fps未達の場合、profiling内訳に基づく原因（エンジン計算 / シリアライズ / HTTP / キャッシュミス）の特定を報告する。

## 最終確認（全タスク完了後）

spec_like_benchmark（default profile、repeat≥5、warmup除外）で以下を一覧報告する：

| 項目 | 仕様目標（27.3節） |
|---|---|
| 教育preview（3f×1λ×25本） | 50〜100 ms |
| インタラクティブ操作（タスク6ハーネスで実測） | 10 fps程度 |
| Spot簡易解析（5f×3λ×512本） | 1秒以内 |
| 詳細Spot解析（9f×3λ×2048本） | 3〜10秒 |
| 周辺光量（9f×1λ×10000本） | 5〜15秒 |
| 最適化粗評価（1候補） | 100〜500 ms |

最終計測も `bench_results/` のJSON履歴に記録し、report.py の推移グラフでタスク0時点からの改善履歴を確認できる状態にする。

未達項目があれば、per-ray / per-surface 単価の内訳と、どの段階（aiming / trace / 後処理 / オーバーヘッド）が原因かを profiling metadata に基づいて報告する。
