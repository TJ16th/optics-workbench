## 実装調整

P3-2〜P3-4ではdrag中previewのdebounceを `180 ms` としていた。P003の軽量previewではエンジン側が十分速く、体感遅延の主因がUI debounceだったため、P3-5で `70 ms` に調整した。

## 計測条件

- API: local FastAPI, `http://127.0.0.1:8000`
- Fields: 3
- Wavelengths: 3
- Drag preview: `samples_per_field = 5`, `ray_aiming.mode = paraxial`
- Commit preview: `samples_per_field = 9`, `ray_aiming.mode = paraxial`
- Repeats: 20
- Effective UI latency: `70 ms debounce + HTTP end-to-end median`

## 切り分け

- P003のPhase 3操作では、エンジン内部profilingはおおむね `2〜13 ms` 程度だった。
- group shiftは既存登録済みsystemを使うため、HTTP end-to-endでも中央値 `5〜10 ms` 程度。
- apertureは半径変更をsystem変更として扱うため、register+previewになり、HTTP中央値は約 `30 ms`。
- decenter/tiltはruntime layoutと回転計算が入るため、group shiftより重いが、中央値は約 `19 ms` に収まった。
- したがって、P003のP3-2〜P3-4操作では、現時点の主因はエンジンではなくUI debounceと、aperture時のregister往復である。

## 既知の制約

- `aperture_stop` 半径変更は現状system再登録を使う。今後 `iris_radius_mm` をruntime configurationとしてエンジンAPIが受けられるようにすると、aperture操作のHTTP overheadをさらに減らせる。
- 仕様に近い10〜20面・非球面・full ray aiming・複数field/波長の重い条件では、過去報告どおりper-ray Python kernelとfull aimingが支配的であり、`doc/work_orders/active/codex_performance_work_order.md` のタスク3以降が必要。
- 現在のP3 UIはdrag中を `paraxial` / 少数光線に固定しているため、教育previewとしては軽快だが、重い解析品質の結果はdrag終了後の通常preview/analysisで見る設計。
